# Reviewer #3 — Technical & Code

## What the evidence says the game is
FightCamp is a Godot 4.7.2 management/fight-simulation game. The current branch (`kimi/km1-game-review`) is built from the `master` lineage up to the KM1 review landing. The technical architecture is:

- **Career/state layer**: `GameState.gd` (17,654 lines, 674 functions) is the autoloaded owner of save/load, world population, roster, gym, booking, and fight setup.
- **Fight engines**: two engines coexist.
  - `FightSimulation.gd` — round-by-round atomic engine for rulesets that are not realtime-enabled.
  - `FightRealtime.gd` + `FightBeatAdapter.gd` — 20 Hz realtime engine + beat adapter for `boxing`, `mma`, `kickboxing`, `muay_thai`.
- **Presentation layer**: `FightWorldLiveScreen.gd` (5,143 lines) drives the 3D room, pairs, grapple films, contact solve, camera, and rope/limb clamps; `FightStagePlayer.gd` (4,894 lines) plays retargeted clips, foot-lock, aim, and contact pushes.
- **Animation pipeline**: `FightClipRetarget.gd`, `FightClipFootPlant.gd`, `FightBodyCapsules.gd`, `FightBodyLayers.gd`.
- **UI kit**: `UIKit.gd` / `UITokens.gd` / `RingStagePanel.gd` / `FightNightScreen.gd`.

The active milestone is **S123 — Playable with a Boxer**. The roadmap says the realtime engine and career loop are functional, but the 3D presentation layer still has a cluster of red tests (body overlap, body layers, pair live, stage realism, ring position, footwork economy, etc.).

## Strengths to protect
1. **Deterministic seeded simulation**. `FightSimulation.begin_fight` seeds a main RNG plus separate judge/burst/consistency RNGs (`FightSimulation.gd:545-634`); `FightBeatAdapter` explicitly draws no RNG (`FightBeatAdapter.gd:35`). Seeded replay is a real asset.
2. **Pure, testable presentation primitives**. `FightPresentationQueue.gd` is static state-machine code with no timers/signals; `FightBeatAdapter` converts engine ticks to beats without inventing events.
3. **Well-documented constants tied to research**. `FightSimulation.gd` anchors numbers to J20, U73, Q75, etc., and explains *why* each constant is what it is.
4. **Token-driven UI kit**. `UIKit.gd` builds instruments from `UITokens.gd` primitives; this is the right foundation for preventing visual drift.
5. **Careful save rotation**. `GameState._write_save_atomic` writes to `.tmp`, rotates `.bak`, then publishes (`GameState.gd:3281-3307`). Losing a save to a half-write is unlikely.
6. **Defensive engine selection**. `FightNightScreen.ruleset_uses_realtime` is an explicit allow-list (`FightNightScreen.gd:52, 282`), so unsupported rulesets fall back to the atomic engine rather than breaking.

## Bottom line for the lead developer
The simulation core is in better shape than the 3D room: seeded determinism, save rotation, and ruleset-aware scoring are solid. The immediate technical blockers are all in the presentation/performance layer: the body-overlap test is genuinely failing, the room is doing expensive work every frame, and the nightly suite has a large red backlog. Fix the overlap allowance table and the per-frame `load()` calls first — both are small, high-impact wins — then profile `_process` before adding more visual features. The 17,654-line `GameState.gd` is a long-term maintainability risk that should be split as soon as the milestone pressure eases.
